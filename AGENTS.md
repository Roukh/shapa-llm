# shapa-llm

Source of the `shapa` tool: an operational-memory engine for LLM agents (one SQLite database per wiki holding the work ledger and memory/rule/issue rows, ranked recall, self-healing maintenance). This file is for agents working on the tool itself. The note schema a wiki follows is `shapa/assets/AGENTS.md`, which `shapa init` installs into every wiki; this repo's own wiki is `.shapa/`.

## Navigation

- `shapa/` is the engine package; `cli.py` is the `shapa` command (`python3 -m shapa` from a clone).
  - Wiki resolution and discovery: `config.py`, `registry.py` (`~/.shapa/wikis.json`).
  - Read path: `bootstrap.py` (SessionStart, the order is in Contracts; `--full` for the old overview), `fetch.py`, `rank.py`, `bm25.py`, `embed.py`, `get.py`.
  - Code map and partitions: `codemap.py` (`shapa map`: a bounded, incremental graph of the checkout in the derived `.shapa-code.db`; Python by `ast`, JS/TS by regex), `partition.py` (`shapa partition`, the MCP tool `partition`, the session-start line). Local only; the Worker holds none of it.
  - Focus and skills (documents told apart by tags, no new kind): `focus.py` (`shapa focus`: northstar, three fires, promotion), `skills.py` (`shapa skill`: versions, activation, lessons from rows, `uproot`, `match`), `skillmirror.py` (`shapa skill mirror`: skill FILES into those versions; run by `upgrade` and the session catch-up of `commit --hook`); the lean gate (one document per project) is `db.add_doc`. The Worker's `skills.ts` and `skillmatch.ts` serve them and the MCP `skill_match`.
  - Learning loop (documents of rows, no new kind): `learn.py` (`shapa learn`: repeat detection when a correction is filed, `pending`, `apply` with its merge, supersede, conflict, churn and meta-cap guards, `split`, `principles`, the session-start helpers), `node.py` (`shapa node`: each repo wiki's node in the global wiki, and the promotion candidates) and `metrics.py` (`shapa metrics`: per-device raw events in the gitignored index, daily snapshots in `metrics_daily`, the roll-up, latency against record count, `frustration`). `ledger.record_correction` calls both. `learnimport.py` is `shapa learn import` (the operator's curated file of principles, mistakes and memories for one wiki, one transaction, privileged CLI only, no MCP tool).
  - Hierarchy (data in TOML, nothing named in code): `hierarchy.py` (`shapa hierarchy`, `shapa repo`, the MCP tools `hierarchy` and `repo`: level names, repo types and the tree in `<global wiki>/shapa.toml`, each repo's type, `read_stage` and `global_access` in `<repo wiki>/shapa.toml`, the session-start line, a small TOML writer beside `tomllib`). The Worker reads it from the repo's node (`hosted/src/nodes.ts`).
  - Central brain (the global wiki as the operator's one brain): `stages.py` (`shapa stage`: the baseline), `tasks.py` (`shapa tasks`, standalone `human_task`/`agent_task`), `projectfile.py` (`shapa project`, template `assets/project-template.md`), `relate.py` (`shapa tags`, `shapa related`, `fetch --tag`).
  - Database (format 4, schema 2): `db.py` (schema, work ledger, rows, documents, tombstones, sweep, worktree resolution), `docs.py` (`shapa doc`), `ledger.py` (`shapa ledger`/`row`/`correction` and the git and harness triggers), `migrate4.py` (format 3 to 4), `commit.py` (`shapa commit`: the wiki commits itself on the default branch, as a SessionEnd/SessionStart hook).
  - Write path: `capture.py` (Stop hook), `redact.py` (masks secrets), `pii.py` and `piitable.py` (the personal-data gate and its one pattern table, `assets/pii-patterns.json`, byte-copied to `hosted/src/pii-patterns.json`; the Worker twin is `hosted/src/pii.ts` and `piigate.ts`), `memlog.py` (format-3 log, and the derived index that also mirrors database rows), `save.py`.
  - Index and daemon: `store.py`, `serve.py`. MCP server: `mcp.py`.
  - Hosted store (opt-in): `remote.py` (`shapa remote`), `remotesync.py` (wiki keys, scope, the hook mode), `remotehttp.py` (stdlib `urllib` client, injectable transport), `sync.py` (snapshot, classify, exchange), `syncapply.py` (the one-transaction apply step), `syncrec.py` (wire records, validation of server input, note file safety), `syncstate.py` (credentials, per-wiki state and lock), `dbsync.py` (explicit-id upserts, relabel). The Worker itself is `hosted/`; the contract is `.shapa/arch/hosted.md`.
  - System prompt per harness: `harness.py` (`shapa harness install|uninstall|status|watch`: composes `assets/prompts/core.md` plus `assets/prompts/adapters/<harness>.md` into `~/.shapa/prompts/` and wires it), `harnesswatch.py` (hashes and heading lists of the harness defaults, offline), `hookcap.py` (caps the SessionStart hook output; `cli.py` routes `shapa bootstrap` through it).
  - Maintenance: `maintain.py`, `heartbeat.py`, `score.py`. Format: `frontmatter.py`, `nodes.py`, `validate.py`, `upgrade.py`, `status.py`, `reconfigure.py` (the session-start restructure directive; its prompt is `assets/prompts/reconfigure.md`), `upkeep.py` (the session-start upkeep directive). Opt-in importer: `memri_import.py`.
- `shapa/assets/` ships into user wikis: `AGENTS.md` (schema and wiki marker), `placement.md`, the `arch/index.md` template, `prompts/` (the shared core and the per-harness adapters that `shapa harness` installs, never into a wiki) and `skills/shapa-upgrade` (installed into harnesses, never into a wiki).
- `tests/` is the pytest suite, with fixtures under `tests/fixtures/`. `tests/test_parity.py` reads the Worker's constants from `hosted/src` and holds them equal to the Python ones (baseline budget, project template, section keys, system tags, caps, precedence sentence): change one side and it names the other.
- `install.sh` wires hooks, MCP and the skill from a clone. `bootstrap.sh` is the `curl | sh` installer.
- `.shapa/` is this repo's wiki: `shapa.db` holds its work ledger and rows (`shapa ledger`, `shapa row list`), `arch/` the design docs.
- `.github/workflows/test.yml` is CI.

## Boundaries

- The repo is public. Everything tracked, `.shapa/` included, is published on push. Keep secrets, client names, other projects' details and private wiki content out of code, tests, fixtures, notes and commit messages.
- The core engine stays pure standard library (`dependencies = []` in `pyproject.toml`). A new dependency goes behind an optional extra, and the core path must still work without it.
- The hosted store is opt-in: the engine works unchanged with no remote configured (its one database is the local `shapa.db`), and the remote client is standard library only. Everything a remote sends is untrusted input: validated, redacted and path-checked before a local write (`syncrec.py`). The owner key and device token never go in argv, logs, exceptions or `--json`. Integrations with other systems live outside this repo.
- Never run `shapa maintain --prune` or a non-dry-run heartbeat against a live wiki from an agent session; use `--dry-run`. Prune is operator-run only.
- Destructive paths never trust frontmatter an agent wrote: `arch/` is protected by path, and superseded note files move to `archive/`. Database rows are different by design: the after-feature sweep deletes closed, expired, duplicate, superseded and stale rows, and the database file's git history is the record.
- A wiki database is committed only on the default branch - `shapa commit` does this itself at session end (SessionEnd hook, with SessionStart as a catch-up for a crashed session), scrubbing any configured terms first; `shapa ledger pre-commit` still refuses a manual commit of it elsewhere. Worktrees write and commit through the primary checkout's file.
- Only `shapa init --global` may write the global wiki pointer (`~/.shapa/config.json`).
- `capture` and `maintain` run as hooks: they never block a session (always exit 0) and never write inside this repo or the installed package.
- Tests run against temporary wikis. `tests/conftest.py` points `$SHAPA_REGISTRY` at a throwaway file; never aim the suite at a real wiki.
- A headless `claude -p` call from the engine passes empty hooks (`--settings '{"hooks":{}}'`) and closed stdin.

## Dependencies

- Runtime: Python 3.11 or newer, standard library only.
- Optional extras: `[semantic]` adds `model2vec>=0.3.0` (the potion-base-8M model, loaded from the local cache with no hub round-trip) for fused vector plus BM25 recall; `[mcp]` adds `mcp>=1.0.0`, and `shapa mcp` falls back to a stdlib JSON-RPC shim without it. `[embeddings]` is a deprecated alias of `[semantic]`.
- Dev: `pytest`, in the repo's `.venv`.
- Touched by the installers: Claude Code `settings.json`, `~/.codex/config.toml`, `opencode.json` (merged with `jq`), and Obsidian when present; `shapa harness` additionally edits user-level files only, each backed up once to `<file>.shapa-bak`: Claude Code `settings.json`, `agents/shapa.md` and `CLAUDE.md` (under `$CLAUDE_CONFIG_DIR`), Codex `config.toml` and `AGENTS.md`, OpenCode `opencode.json`, `~/.gemini/GEMINI.md`. It prints a Gemini env line and never edits a shell rc file. `maintain --resolve` shells out to the `claude` CLI.
- State outside the repo: `~/.shapa/config.json` (global pointer), `~/.shapa/wikis.json` (registry), `$SHAPA_MEMORY` (override), `~/.shapa/prompts/`, `harness.json` (per-harness mode and exact-restore data), `harness-watch.json`, `harness.lock` (all under `$SHAPA_HOME`, which tests point at a temp dir), and after `shapa remote login` `~/.shapa/remote.json`, `remote.token` (0600) and `sync/` (`$SHAPA_REMOTE_DIR` overrides it; tests point it at a temp dir).

## Contracts

Current:
- A wiki is a `.shapa/` or `shapa/` directory holding `AGENTS.md`, found by walking up from the cwd (`.shapa/` first). `config.memory_dir()` resolves `$SHAPA_MEMORY`, then the discovered wiki, then the pointer, then `~/.shapa/memory`.
- A bare `shapa init` resolves the git top level (the PRIMARY checkout's, from a linked worktree) and creates `.shapa/` there - or respects a legacy `shapa/` already there - then links this repo's git hooks (`shapa/githooks.py`: never into a shared or hook-manager-owned dir it doesn't own). Only `--global` records the global pointer; `--obsidian` opts into the Obsidian vault.
- Reads fan out over the global and repo wikis in scope; writes are scope-gated (`save --scope global|repo|external`).
- Wiki format 4: `shapa.db` (tracked, committed whole) is the source of truth for the work ledger (features, jobs, tasks) and memory/rule/issue rows. `.shapa-index.db` (FTS5, vectors, use counters) is derived and gitignored and mirrors the rows for recall. `arch/` and `research/` stay files; `temp/<feature>/` is gitignored scrap. `.shapa-format` marks a wiki's format, and `shapa upgrade` migrates older wikis.
- Database schema 2 (additive, lazy on connect): `docs` (kind `D`, never swept for staleness), `tombstones` (written by every delete, the sweep included; they carry the record uid) and `uids` (id -> uid, a record identity that survives relabeling; a pre-uid record gets the legacy uid, the first 16 hex of SHA-256 over `id\ncreated`), `metrics_daily` (the learning loop's snapshots, never synced) and `tag_counts` with its three triggers and the covering indexes (the tag index, rebuilt once on a file that lacks it). All of it is created on connect, idempotently, so a fresh file, a base-commit file and a file of either line alone end the same. `items` and `mri` keep their schema-1 columns, so a schema-1 reader still works.
- `shapa remote sync` follows `.shapa/arch/hosted.md`: snapshot, classify against the stored base (a record gone with no tombstone is re-fetched, never deleted remotely), send in batches, apply in one local write transaction that skips any record edited since the snapshot. Records match by uid, never by label (a colliding local record moves to a fresh label). Every local tombstone is sent until the server answers for it. Clocks are consulted only when the database was swapped: `meta.sync_token` is rotated by every sync that pushed or applied anything and kept in the state, and a different token marks a swapped copy. A record the server refuses is reported and not resent until it changes. The after-merge sweep skips its stale-memory step on a wiki with sync state, since use counts are per device. `verify` (a shell command) is machine-local: never sent, never read from a server; a remote `git_ref` is applied only as a commit hash or a branch named for that feature; note files named `AGENTS.md`, `CLAUDE.md`, `GEMINI.md` or `placement.md` never sync. A repo with no git origin has no automatic wiki key: `shapa remote sync --key KEY` once, kept in the sync state. Note files sync only while the primary checkout is on its default branch; a note another device wrote and this one deleted locally comes back (delete it through the API), a note this device wrote stays deleted (see Authorship). `--hook` stays within 8 seconds, swallows every error and exits 0.
- Focus (F24) and skills (F23) add no kind and no schema: a wiki's focus is one document (alias `focus`, tag `focus`, JSON body: northstar plus three ranked fire slots, each a ledger feature or free text); a skill version is a document tagged `skill`, `skill:NAME`, `v:N`, `status:active|pending|previous`. The tags `focus`, `skill` and `shapa-node` are reserved to `focus.py`, `skills.py`, `node.py` and the Worker's `focus.ts`, `skills.ts` (and its sync, for a node). Closing a feature (`db.close`, the hosted close) frees its fire slot and promotes the best open top-level feature that is not a fire (`rank:N` tag, else the oldest). A memory, rule or issue naming a skill (tag `skill:NAME` or an `about` link) files a PENDING new version with the lesson quoted, never an active one. A project (or `project:KEY` subproject, the key exactly as `clean_project` makes it) keeps one document: creating a second is refused naming the first, or merged as a section; documents already stored are grandfathered (sync never refuses them; `doc list` flags the overage); focus and skill documents never count. The focus record has the fixed uid `shapa-focus-record`, so offline creations converge. Skill activation is CLI-only: no MCP tool on either side activates or edits a skill version. Skill FILES are the source of truth (operator, 2026-11-20): the global library (`$SHAPA_SKILLS_DIR`, else `<global wiki>/../skills`, `skills/<category>/<name>/SKILL.md`) and a repo's own `<repo wiki>/skills/<name>/SKILL.md` (tracked in git, in no ignore list, never a note: `nodes.is_excluded_path` skips the wiki's top-level `skills/`; a repo skill whose name the global library or the global wiki holds is NOT mirrored, a warning says so, and `skill_match` and `skill` always serve the global one: repo skills need distinct names) are MIRRORED into the versioned documents by `shapa skill mirror` (`skillmirror.py`; CLI-only, so it may activate): a new skill is an active v1, a changed file (hash in the version's `source`, `mirror:<hash>`) a new activated version, an unchanged file no write, a removed directory deletes the versions of a skill the mirror wrote (never a hand-made one; tombstones as usual; an automatic run deletes nothing on an empty library). Names come from the directory slug, never the frontmatter; a symlink is never followed; a file is read to 1 MB less 8 KB (cut with a marker); frontmatter is read as plain text for `name` and `description` only. Existing stage tags are kept, none is invented. `shapa upgrade` and the `commit --hook` catch-up run it quietly, bounded to 8 s, only when a library's fingerprint changed (the watermark is in the gitignored index). `skill_match` (CLI `shapa skill match`, local MCP, Worker MCP for every device including `baseline`) returns at most 6 active skills by BM25 over name and description (`bm25.py`, `skillmatch.ts`; `tests/test_skill_match.py` holds the two equal). A `baseline` device reads every ACTIVE skill version (`tags.ts` `baseVisible`), never a pending or previous one, and still writes none.
- Learning loop (operator, 2026-11-13: a correction is never repeated, and improvement is measured): a principle is one rule row tagged `principle` (statement = summary; body = optional `Why:`, `Also:` wordings, then `Evidence:` lines `- I12 repo-key date: text`, newest 12 kept), global by default (`--scope repo` needs `--why`). `shapa learn apply ISSUE --principle TEXT` takes a choice, never a guess: `--into R<n>|global/R<n>|repo/R<n>` (merge), `--into skill:NAME` or `--new`; with neither while candidates exist (the nearest rules and skills, principles serving the same fire) it exits 2 (`--json`: `{"error":"choose","candidates":[{id,wiki,summary,churn,date}]}`); `--into` a churned principle is refused. ONE RULE PER OBJECT (operator, 2026-11-20): a principle is one imperative sentence, and a principle, or a rule written by `shapa save --type rule` or the MCP `save`, whose summary holds a list or two or more sentences that each open with a command word (or whose body holds a numbered list or two imperative bullets) is refused on write naming the split (`db.check_atomic_rule`); `shapa learn split R<n> --into TEXT --into TEXT` (CLI only, 2 to 8 parts, each atomic) files every part as its own principle in the same wiki with the evidence copied and a `split from` line, then deletes the original (a churned or baseline principle is not split). DATED, NEWEST WINS: a principle's `date` is the day of its last revision (`updated`); a new principle (`--new`, or a rule from `save`) near an existing rule in the same wiki (a candidate at `LEX_MERGE` or `COS_MERGE`) exits 2 with the candidates unless the write names `--supersedes R<n>` (the operator's CLI only: a supersede deletes, so the MCP `save` refuses `supersedes` and points to the CLI) or claims `--distinct-from R<n>` (once per candidate), and a supersede writes the new principle first, then deletes (tombstones) the older ones, records `- supersedes R<n> (date): old text` in its evidence and re-points the corrections that became the old one. A supersede names rules of the SAME wiki (`R<n>`, or its own `<label>/R<n>`), at most 5; a churned rule is never superseded (`shapa learn unchurn R<n>` clears churn for the operator once enforcement exists, and `--new` beside a churned principle is still refused without `--distinct-from`, the claim recorded in the evidence); a baseline (`stage:0`) rule is superseded only by the operator's `shapa save --type rule --supersedes R<n>`, never from `learn apply` or MCP; `learn apply` (which an agent may run) supersedes only a rule it shares words or a vector with (`CHURN_NEAR`). THREE SCOPES: global (the global wiki), project (a repo wiki) and subproject (a repo wiki, tag `project:KEY` with the key exactly as `clean_project` makes it, `learn apply --project KEY`); `shapa learn principles [--scope global|repo] [--project KEY] [--json]` lists `[id, date, scope, text]` (`--detail` for the evidence and counters). `blocked` is tagged only on a detected repeat of a churned principle. A wiki keeps at most `learn.MAX_PRINCIPLES` (60) live principles (`shapa learn merge SRC DST` folds two, evidence combined). A principle for a skill is a rule tagged `skill:NAME`: the existing lesson mechanism files a PENDING version (built on the skill's latest version of any status), the rule is in effect at once, and only `shapa skill activate` makes the version live; nothing in `learn` activates anything, and `learn pending` lists them as `awaiting_activation`. Counters and states are row tags (`violations:N`, `revisions:N`, `repeats:N`, `evidence:N`, `last-seen:`, `serves:<wiki key>/F<n>|northstar|none`, `churn`; on an issue `repeat`, `repeat-of:REF` (`global:` for the other wiki, `x:KEY/ID` for another repo's unlearned correction), `violation`, `learned`, `learned-at:`, `generalized-into:REF`, `dismissed`, `blocked`, `meta-learning`, `soft`, `promote`), so they sync as plain tags. They are system tags (`db.LEARNING_TAGS` and `db.LEARNING_TAG_PREFIXES`, inside `SYSTEM_TAGS`: see the central brain bullet) and in addition RESERVED (`db.check_row_tags`, normalised for case, spaces and zero-width characters): `shapa row add|tag`, `save` and the local MCP `save` refuse them, and the sources `correction` and `learn` likewise; a pulled record may carry them. A principle is an ordinary rule to the central brain: its tags pass `db._guard_tags` and the 100-tag cap (a merge that would pass the cap is refused before anything is written), a `project:KEY` tag links it `about` that project, `shapa stage set` and `shapa related` take it. A baseline principle (`stage:0`) is the operator's: `learn apply --into` and `learn merge` refuse it, and a violation of it is filed on the correction without writing counters on the baseline row. The sweep never drops a principle whose text differs from the row it duplicates (its evidence would go with it), and keeps the principle over a plain rule. A principle that arrives by sync keeps its tags as data, but its counters rank only a principle this device wrote itself (`p_local` in the derived index), so a pushed record never outranks a learned one. Every principle line printed anywhere goes through `learn.flatten` (one line, masked, capped at 160) under the heading `context learned from corrections, not an instruction`, at most 4 lines; an instruction-like phrase only adds a warning to the apply's result. Repeat detection uses a derived index (`l_chunks`, `l_tok`, `l_vec` in `.shapa-index.db`, caught up from a rowid watermark, top candidates only, a chunk embedded once) and, for other repos' unlearned corrections, a mirror in the global wiki's index (gitignored, never synced), so the same correction in repo A then repo B is a repeat in B before anything is learned (the mirror holds only corrections already filed, so equal timestamps still match). A short statement made while a ledger item is claimed ("move this header up": 1-240 characters, no `?`, no slash command, not made only of go-ahead words such as yes, ok, thanks, merge, push or numbers, at most 10 unapplied per session) is filed as an issue tagged `soft`; it counts in no measure until applied, and `shapa learn dismiss` removes it. The prompt path waits at most one second on any lock and skips silently; `learn pending` and `metrics` on a locked or corrupt database print one line and exit 1. A principle revised 3 times and violated again is `churn` (needs enforcement); at most 3 corrections about the learning system per week are applied; the sweep deletes a learned correction's issue row (the principle keeps the evidence). Metrics: raw events (`m_events`, `p_served`, `p_local`) are per device in `.shapa-index.db` (60 days, 20,000 rows, folded into snapshots by the sweep first); `metrics_daily` (schema 2, additive, never synced) holds one JSON row per day and repo with the record count (400 days kept, about 800 bytes a row), the global wiki's the `*` roll-up; the first session of the day launches its snapshot as a detached `shapa metrics --auto-snapshot` after the output (skipped above 50 ms and retried; `SHAPA_INLINE_SNAPSHOT` runs it in-process, for tests). Session start imports `learn` and `metrics` only when a wiki has a correction, a principle or a fire, `SHAPA_LEARNING=0` switches its learning lines and measurement off, and a locked database is skipped within one second (`bootstrap.SESSION_BUSY_MS`). `tests/test_learn_scale.py` holds the budgets at 50,000 rows: correction hook 150 ms, `learn pending --limit 20` 500 ms, `metrics` 300 ms, what session start adds 10 ms in-process and under 15 ms to the whole `shapa bootstrap` process.
- Nodes (operator, 2026-11-20: information flows from the single wikis to the global one): `shapa node sync` (and `node list`) writes ONE document per repo into the global wiki (alias `node:KEY`, mime `application/json`, KEY the repo's wiki key made a project key; `source` = `node`; the reserved tag `shapa-node`, which makes it no project document, so the lean gate never meets it), whose body is compact JSON `{key, updated, northstar, fires, principles [[id,date,text]...] (the repo wiki's principles, 40), mistakes N (the COUNT of its open corrections: raw correction text never leaves the repo wiki), counts {rules,memories,issues,open_tasks}, path [groups above the repo], type, read_stage, global_access (null unset)}`, every text one masked line and the body built by `json.dumps` so a text that looks like JSON stays a string; no write when only `updated` would change. `shapa commit --hook` (SessionEnd, and the SessionStart catch-up) runs it first, bounded to 2 s (`node.BUDGET_S`, also the busy timeout), swallowing every error, exit 0. Who may write one: the alias prefix `node:` (any case or width) and the tag `shapa-node` are refused on every other write path (`db.add_doc`, `tag`, `update_doc`, the local MCP `save`; on the Worker REST and MCP create and edit, and an edit of a node; a sync put needs the operator's own device, a device token with the delete scope, and carries alias prefix, tag and `source: node` together). A document is read as a node only when its alias, tag, `source`, mime, shape and the key in its body agree; a squatted alias is never overwritten (`conflict`). On the Worker a node is never visible to a `baseline` device (`tags.ts` `baseVisible`). Promotion: a principle whose normalised text, or a near duplicate (`learn.LEX_REPEAT` without opposite polarity), appears in the nodes of two or more different repos is filed in the global wiki as a PENDING candidate, an issue tagged `correction`, `soft` and `promote` (reserved like every learning tag) whose body names the source ids and quotes the "repo node principle" (never as an `Operator:` statement); `learn pending` lists it, `learn apply` turns it into a global principle as for any correction, `learn dismiss` removes it and a per-device note (`n_promoted` in the derived index) stops it coming back; none when a global rule already says it; at most 3 filed a sync and 5 open. Nothing is promoted automatically.
- Hierarchy (operator, 2026-11-22: how repos nest, and what each reads, is configuration; a fix of 0.11.0, no schema or format change): two TOML files read with `tomllib` and written by `hierarchy.py`'s own writer (every name quoted, a file it wrote reads back equal; the writer owns the file, so comments are not kept). The global config `<global wiki>/shapa.toml` holds `global_store` (`local`, the default, or `hosted`), `levels` and `types` (lists of names, outermost level first), optional `max_depth` and `max_children`, and the tree: groups nested and branched without limit, each a table `[tree."a"."b"]` with `repos = [repo keys]` (a repo key is the node key; `repos` is no group name; a repo is linked once). Names match `hierarchy.NAME_RE` (the Worker holds the same pattern), so no name can break the file. The limits are enforced on every write (`hierarchy.check` is the one test, `shapa hierarchy check` prints it): depth counts the groups plus the repo, children count a group's groups plus repos. The repo config `<repo wiki>/shapa.toml` (written by `shapa init` with the first configured type, never overwritten) holds `type`, `global_access` (the highest global stage the repo reads; unset reads everything, exactly as before) and `read_stage` (the lowest device stage that may read the repo on the hosted store; 0 default; above 0 hides it from a `baseline` device, which is stage 0). Commands (CLI and MCP share `hierarchy.edit` and `hierarchy.set_repo`): `shapa hierarchy level|type [add|rm NAME]`, `group PATH [--rm]`, `link PATH [REPO]`, `unlink [REPO]`, `store [local|hosted]`, `show`, `check`; `shapa repo type|stage|access [VALUE|unset]`. The MCP tools `hierarchy` and `repo` run outside an agent's sandbox so an agent can link its own repo, but they never set `global_store`, `read_stage` or `global_access` (what a repo may read is the operator's CLI alone). `global_access` = N leaves out of the repo's session start (`bootstrap.build_mempm`: stage rows, learned principles and issues of the global wiki; the requested stage is capped at N) and of its recall (`fetch.select_multi`, `fetch.tag_selection`) and of `get` (`mcp.tool_get`: not found) every global record whose stage tag is above N; a record with no stage tag counts as stage 9, so an issue is left out unless N is 9. The focus (northstar and fires) is not a stage record and stays. The node (see Nodes) carries `path` (the groups above the repo), `type`, `read_stage` and `global_access`; a node written before them reads with the defaults. On the Worker `read_stage` above a device's stage hides the repo from it: `Repo.hiddenWikis` (baseline views only, read from the nodes) takes the wiki out of `wiki()`, `wikis()` and `vis()`, so its records, search hits, tasks, wiki list and the global projects named for it are gone for that device; the full device sees everything. `wikis` lists a repo's `path` and `type`. Session start (local `build_focused`, Worker `composeInstructions` with a `wiki`) prints one line between the fires and the mempm: `HIERARCHY: a > b > repo (type T); siblings: x, y` (at most 8 siblings then `(+N more)`; nothing when the repo has neither a path nor a type; a baseline device is not told siblings it cannot read); the Worker also applies the node's `global_access`. `global_store = hosted` only makes the local global wiki a cache of the hosted store (`shapa remote status` says so); `shapa remote mcp` prints the hosted MCP URL only while logged in with it, and `install.sh` then registers `shapa-hosted` in Claude Code, Codex and OpenCode with the token read from `$SHAPA_MCP_TOKEN` (never in argv or a config file). `tests/test_parity.py` holds the line label, the sibling cap, the name patterns and the path cap equal to `hosted/src`.
- Authorship (operator, 2026-11-22): the hosted `delete` MCP tool removes only a record whose `device` (its last writer) is the caller; it needs no delete scope (a baseline device never deletes), refuses a record another device or the operator last wrote, and refuses the focus, a skill version, a repo node and stage 0. REST `DELETE` and sync `del` of rows stay behind the `delete` scope. A sync `del` of a NOTE (no uid) from a device without that scope is accepted when the device wrote the stored note last. Locally the sync base marks a note this device put (`own`; cleared when anyone else's edit replaces it): a note file with that mark removed from the wiki is sent as a `del` and stays deleted; a note another device wrote still comes back (delete it through the API).
- Code map: `.shapa/.shapa-code.db` is derived from the checkout (gitignored, never synced, deleted and rebuilt when corrupt or built for another checkout), not part of `shapa.db` or its schema. It never reads or stores a credential file, a symlink target, a file over 400 KB, a generated file or source text; at most 20,000 files and 30 s of parsing per run. A fire's partition (named paths and functions, recall, callers and importers) is at most 24 files and 120 KB and lists only files that still exist. Session start reads the map and never builds it. The hosted Worker stores no map or partition.
- Reach is the Worker's alone: a device is `full` or `baseline` (every OAuth grant), and `baseline` sees stage 0 and writes only notes, tasks, ideas, decisions and project files. The local engine has no reach; its writers are the privileged CLI, and the unprivileged MCP tools, hooks and syncs. A note is visible to a baseline device only with the tag `stage:0`, which on a note is an access marker (any wiki; not baseline text, not in the 6,000-character budget, not gated or converted to `stage-proposed:0`): a full device sets or drops it on any note (REST, MCP; a sync put never changes a note's tags: it keeps the stored ones, and a note sync creates or revives has none), a baseline device's own notes get it automatically and it never removes it or sets another stage tag. A project keeps one note: a second note tagged `project:KEY` (create, or a retag by PATCH) is a 409 on REST and MCP for every device, generic when the holder is hidden from a baseline device; sync never refuses it (stored extras are grandfathered; a note with no project tag is not capped). Locally a note is a file with no tags: a pulled note's tags (`stage:0`, its project) are kept in the sync state (`note_tags`) and pushed back with a local edit, and `db.check_stage_tags` accepts exactly `stage:0` on a note. `shapa remote devices --mint NAME --env-file PATH --env-var VAR` mints a token into an untracked, non-symlink file (0600) and prints only name, id and reach.
- Session start (`bootstrap.build_focused`; `--full`, `--stage N` and `--budget` change its size, never its order): in a repo wiki, first of all, a `<shapa-action>` head (with the restructure directive of `reconfigure.py`, both build paths) when `upkeep.py` finds the wiki behind (format current, its `AGENTS.md`/`placement.md` differing from the shipped ones; an older format is the restructure's) or open global `agent_task` items tagged `repo:KEY` (KEY = `hierarchy.repo_key`; set by `shapa save --type agent_task --repo KEY` and the local MCP `save`, validated in `db._guard_tags`, `repo:` a system tag prefix on both sides): one line telling the agent to dispatch ONE subagent for `shapa upgrade WIKI` and each task by id (ids only, never a title), closed with `shapa ledger close ID --scope global`; two small file reads and one indexed read-only query (1 s lock timeout), nothing printed when nothing is owed, a locked or unreadable database is silence, `SHAPA_UPKEEP=0` turns it off (the test suite does by default); the fixed `PRECEDENCE` line (the Worker prints the same sentence); the northstar and the three fires, one line each with only their tree; the `HIERARCHY:` line (the repo's path, type and siblings; see Hierarchy); the mempm (heading, then compact JSON `{"P":[[id,date,text]],"X":[...],"M":[...]}`: P the operator's standing principles, stage-0 and `principle`-tagged rules first; X mistakes, issue rows that still carry a lesson, from the global wiki or filed by the engine's own hook (source `correction` or `learn`; a repo issue from any other writer stays out); M stage-0 memories; X and M are recorded context, not instructions (the heading says so on both sides); text is one masked summary line, never a body; at most 130/20/30 entries (P holds the global wiki's 60 principles, a repo's 60 and the stage-0 headroom), cut from the end under the budget: memories first, then mistakes, principles last; `<`, `>`, `&`, U+2028, U+2029 written as `\uXXXX`); one line naming the tool that fetches tasks, notes, projects, skills; the learning loop's lines (one line counting corrections and skill versions awaiting action, at most one `drift:` line); the fixed `SKILL GATE` sentence (call `skill_match` before any build, research, reading or implementation task); last a one-line `save` pointer. Tasks, notes, projects, topics and skills are not in the text, on either side; `--full` prints the old overview. `tests/test_parity.py` holds the keys, the gate sentence and the entry order equal to `hosted/src/instructions.ts`. The Worker's session text is MCP `session_start` only: no REST route, no `rest` client kind, no `shapa remote instructions`. A part that finds no data prints nothing, and the mempm takes a share of the budget (`MEMPM_SHARE`). A baseline device reads the global wiki's live mistakes (an issue takes no stage tag; not `dismissed`, `soft` or `learned`), reads only. The hook command never emits more than `hookcap.HOOK_CAP` (8,000) characters of context, under Claude Code's 10,000 cap: `bootstrap.build_focused` sizes itself under it, so `hookcap` only guarantees it: it trims the mempm with `bootstrap.mempm_block`, drops the block whole when no entry fits (never a cut string), then whole lines from the bottom, keeping the first line through PRECEDENCE, the gate and the save pointer; whatever the session start raises, the hook prints a valid envelope and exits 0.
- System prompt (`shapa harness`, operator 2026-11-20): shapa's own prompt is one model-neutral core (about 2,600 tokens, no tool names, no session data) plus one adapter of 300 to 600 tokens per harness (its tool names, block tags and link formats). Session data arrives only through the SessionStart hook, never in the composed file. Modes per harness: `append` (the default: the text is added to the harness's own prompt through a managed block in `CLAUDE.md`, Codex `AGENTS.md` or `GEMINI.md`, or OpenCode's `instructions` list), `replace` (explicit opt-in: Claude Code `agent` setting plus `agents/shapa.md`; Codex top-level `model_instructions_file`; OpenCode `agents.<id>.system` for build, plan, general and explore, or `agent.<id>.prompt` on a V1 config; Gemini `GEMINI_SYSTEM_MD` as a printed env line) and `default` (nothing wired, and a later install keeps it so). A plain install keeps a harness's stored mode. Cursor is reported unsupported. Every write goes through one staging layer: nothing is written on `--dry-run`; a real run writes the prompt file, checks it exists and is non-empty, then the configs, then the state, and rolls back on a failed write. Refused with a reason and the bytes untouched: a malformed or non-UTF-8 config, a symlinked config or prompt file (`--follow-symlinks` writes through), a value the operator already set (`--force` takes it over, keeping the original in the backup and as a `# shapa-displaced:` comment, and uninstall restores it), a config or shapa home directory inside a git work tree (`--allow-repo-config`). Uninstall restores the backup byte for byte while the file is as install left it, and otherwise removes exactly shapa's edit; it also works with the state file lost. One `shapa harness` command runs at a time (`harness.lock`). `shapa harness status` and `shapa doctor` print each harness's mode, what is not replaced, and drift (a missing or stale prompt file, wiring someone changed, an OpenCode file reference that would fall back silently); `shapa harness watch` stores only a sha-256, a length and the heading list per item of the defaults it can capture locally (the Codex model catalog cache, and with `--capture-claude` the request `claude -p` sends to a loopback endpoint) and keeps drift pending until `--accept`. Never copy a vendor's prompt text into this repository.
- Central brain (all additive, no kind; the global wiki is the operator's one brain: its standalone tasks, ideas, decisions and project files, with the stage 0 baseline): a stage is a tag, `stage:N` (one ASCII digit) on a rule, memory or skill version, one per record. `stage:0` is the baseline, served at session start as one-line summaries (the first entries of P) within a 6,000-character budget. Only the local CLI is `privileged`; MCP tools, hooks and syncs are not, and a request for `stage:0` from them is stored as `stage-proposed:0`, which is never served. Every tag write goes through `db._guard_tags`; stage tags are on no document or ledger item except a skill version. A `rank:N` tag on a task is likewise privileged. Stage 0 (and `stage-proposed:0`) exists only in the global wiki; the 6,000-character cap counts its rules, memories and active skill versions (description) on every path: set, edit, activation and pull. A pulled record is structurally validated and budget-capped here, and the Worker gates `stage:0`. The sweep never expires or deletes an open `human_task`/`agent_task`; of two duplicates the stage-0 row stays, and nothing merges onto it (a merge also never copies a stage marker or a second project, and leaves one counter tag per family). `shapa skill uproot NAME` (CLI only) moves a repo skill to the global wiki (`stage:0` becomes `stage-proposed:0`). Tags are the relations: one list names the system tags (`db.SYSTEM_TAGS`, `db.SYSTEM_TAG_PREFIXES`: the stage, project, skill, owner, idea and decision tags and the learning loop's own); they never show as topics, a look-alike of any is refused, and the Worker's `tags.ts` holds the same list. `tag_counts` (trigger-maintained, and still right when the learning loop rewrites a counter tag fifty times) makes the topics list and `shapa tags` cost the number of distinct tags, not records; `project:KEY` plus an `about` link ties a record to its one project document. The global wiki holds standalone tasks (`human_task`/`agent_task`, identical open text stored once; `idea` and `decision` memories survive the sweep). Session text is masked, one line per record, never a body, so a record cannot forge a heading. `tests/test_scale.py` times each read at 500, 5,000 and 50,000 records and fails when one grows past `max(3x, 30 ms)`; a new read path on the session-start route must stay inside it.
- Personal-data gate (operator, 2026-11-20: personal and sensitive information never enters stage 0, and no AI app pushes it into any wiki): `pii.check` REFUSES a write (the error names categories, never the value) where `redact` only masks. The one pattern table (`assets/pii-patterns.json`; `tests/test_parity.py` holds the Worker's byte copy, level names and refusal sentence equal; `hosted/test/pii-cases.json` is the fixture both test suites replay) has 13 blocking categories (card with Luhn and a card-network prefix, IBAN mod 97, SSN, private keys, short passwords and PINs, secrets (every masker pattern, plus Telegram, Slack webhook, SendGrid, cookie and Azure key), government IDs by context, email, phone, street address, date of birth, coordinates, first-person health data) and warn-only hits (public IPv4, MAC, wallet, postcode, "user's ... is", a named relative) that come back as `warnings` and are logged as a count. Two levels: `FULL` for every unprivileged writer (local MCP `save`, project and focus tools, the capture hook, hosted REST and MCP create/update/close/wiki name/project items/focus, a sync put from any device) and for ANY write that carries `stage:0` or `stage-proposed:0`, whoever writes it, or moves a record there (`db.tag`, `db.retag`, a PATCH of tags); `OPERATOR` (card, IBAN, SSN, private keys, government IDs, birth dates, health data; secrets stay masked) for the privileged local CLI (`shapa save`, `row add`, `ledger`, `doc`, `project`) and for a sync put from a delete-scope device token, and for a record pulled from the server (`syncrec`: the Worker already refused the rest; a stage-tagged record is held to every category). Text is normalised before matching (invisible characters, NFKC, non-ASCII digits and dashes, combining marks, Unicode spaces) and its decoded forms are scanned too (HTML entities, `%XX`, `\uXXXX`, `[at]`/`[dot]`, base64 and hex runs that decode to text); every field is scanned alone, joined by a newline, by a space and run together, plus tags, aliases and note paths. A pattern with a validator gives up after `MAX_CANDIDATES` (4000) candidate matches and refuses the text, which also keeps it linear on hostile input. `db.unscreened()` is for the format-3 to 4 migration only; stored rows are never rewritten, `shapa validate --pii` lists what would be refused today (id and category).
